### Source PWM table (not a hardware-approved pin map)

The following entries are explicit in C's `pwm-pin-gpios` and `pwms` arrays. CHnN denotes a complementary timer output; the overlay supplies `STM32_PWM_COMPLEMENTARY` for those pins.

| Header | Pad | Timer/channel | Advertised six in manual? |
|---|---|---|---|
| D2 | PB3 | TIM2 CH2 | No |
| D3 | PB0 | TIM3 CH3 | Yes |
| D5 | PA11 | TIM1 CH4 | Yes |
| D6 | PB1 | TIM3 CH4 | Yes |
| D7 | PB2 | TIM8 CH4N | No |
| D8 | PB4 | TIM3 CH1 | No |
| D9 | PB8 | TIM4 CH3 | Yes |
| D10 | PB9 | TIM4 CH4 | Yes |
| D11 | PB15 | TIM1 CH3N | Yes |
| D12 | PB14 | TIM1 CH2N | No |
| D13 | PB13 | TIM1 CH1N | No |
| D20 | PB11 | TIM2 CH4 | No; conflicts with Wire SDA use |
| D21 | PB10 | TIM2 CH3 | No; conflicts with Wire SCL use |

No enabled header PWM entries for D0/D1, D4, or A0–A5 in this snapshot. LED3 RGB additionally maps TIM5 CH1/2/3. The overlay's repeated comment about enabling only marked pins is stale relative to its actual arrays; arrays, installed generated devicetree, and hardware must agree before use.

### Additional source concern: matrix bitmap path

C `Arduino_LED_Matrix.h` declares `_frameHolder[3]`, while `loadPixelsToBuffer()` for 104 pixels writes three complete 32-bit words and one remaining word; `loadFrame()` reads four words. This is a source-level apparent out-of-bounds defect in `renderBitmap()/loadPixels()`, not a reproduced target failure. Use the independent 104-byte `draw()` path or a caller-owned four-word `loadFrame()` buffer for the P0 demo; do not patch third-party code or claim the installed library is affected without checking it. Regression: host sanitizer harness around this conversion or upstream-fixed version comparison, plus target compile/render inspection. `playSequence()` is also unsuitable after setup under R4 because it blocks; no conflict is resolved by hiding that call in a library.

Thus the PWM mapping and apparent bitmap defect above also appear in this release source. This comparison is narrower than certifying the entire release or its binary loader.

Read-only examination of release [`loader/matrix.inc`](https://github.com/arduino/ArduinoCore-zephyr/blob/79b3f1afdad455f55e4a25030953617152c0227c/loader/matrix.inc) verifies `matrixGrayscaleWrite()` copies exactly 104 bytes into a static framebuffer and assigns a color flag, with no allocation, wait, or input-dependent loop in that function. `matrixBegin()` configures a timer callback every 10 us; the callback updates one matrix LED. Therefore `draw()` is a bounded source path suitable to investigate for the inert demo, but matrix interrupt load still affects total timing. Use 104 valid bytes, `setGrayscaleBits(3)` and pixel values 0..7; ISR switch behavior does not define every out-of-range value. Keep matrix-active measurements separate from timing-only measurements. This proves neither target linking nor on-board execution time.
