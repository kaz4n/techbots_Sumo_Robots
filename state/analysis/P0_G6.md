### Timing arithmetic and library fault behavior

For a register-pointer write followed by a read of N data bytes, the ideal clock count is `9 * (1 address-write + 1 register + 1 address-read + N data)`. Each term includes ACK/NACK. This omits START/STOP timing, bus-free intervals, stretching, driver work, interrupts and scheduling; it is a lower bound, never WCET.

| Operation | Ideal SCL clocks | At 400 kHz | At 100 kHz |
|---|---:|---:|---:|
| One coherent 14-byte sensor burst | 153 | 382.5 us | 1530 us |
| One extra 1-byte status or configuration read | 36 | 90 us | 360 us |
| Adafruit 2.2.9 complete `getEvent()` read path | 225 | 562.5 us | 2250 us |

The final row includes the 14-byte burst plus separate accelerometer-range and gyro-range reads. Calling separate sensor-object `getEvent()` methods repeats acquisition. Adafruit output events use acceleration in m/s^2 and gyro in rad/s; convert deliberately for the project's G/DPS units.

**DESIGN IMPACT / candidate-library adoption blockers:** `Adafruit_MPU6050::_read()` ignores the boolean return of its burst read into an uninitialized local buffer, while `getEvent()` always returns true. A failed transfer can therefore produce invalid values without an error indication. The initialization/reset path has an unbounded reset-bit polling loop; allocation and delays also occur in setup. This library is useful source evidence and a compile-probe candidate, not an accepted failure-safe HAL. A future integration must expose real transfer success, validate configuration, bound initialization, and publish only complete valid new samples. No third-party patch or driver is implemented here.

BusIO `write_then_read()` requests a pointer-write/read transaction with `stop=false` by default. Core 1.0.0 Wire ignores `stopBit` and makes separate synchronous `i2c_write`/`i2c_read` calls. Verify the resulting waveform against the sensor read protocol; do not claim the requested repeated START is honored. A successful bench read alone would not establish the fault-time bound.

The pinned research Zephyr [STM32 Kconfig][mpu-timeout] defaults `CONFIG_I2C_STM32_TRANSFER_TIMEOUT_MSEC` to **500 ms**, with minimum selectable value **1 ms**. Its [v2 driver][mpu-driver] uses that timeout for completion, while the [common transaction entry][mpu-entry] takes the bus semaphore with `K_FOREVER`. Consequently this source path cannot be presumed to meet an 800 us complete synchronous tick under faults or contention, even if ordinary transfers are fast. The installed loader's revision, config and driver selection remain unknown. This is a concrete R4 dependency, not evidence that this board actually uses the 500 ms default.
